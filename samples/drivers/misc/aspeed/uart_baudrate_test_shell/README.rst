.. _aspeed_uart_baudrate_test_shell:

Aspeed UART baud rate loopback test shell
#########################################

Overview
********

A shell command that tests the baud rate of two UARTs wired to each other. It
runs on ``ast1040_evb/ast1040/cm4``. Any UART can be tested, except the one
that carries the shell.

Wiring
******

The sample does not know how the UARTs are connected. Wire two UARTs by hand
(TX of one to RX of the other, both directions, common ground) and pass their
names to the command. The ``uart_routing`` driver is not used or changed. Note
that the UART driver clears the routing selector bits of uart0 to uart3 at
init, so the routing state depends on the boot-time register value.

Usage
*****

.. code-block:: console

   uart_baud <uartA> <uartB> <baud|auto|auto_hs> [inc|fixed] [len]

* ``auto`` as the baud runs 1200, 9600, 19200, 38400, 57600 and 115200 in
  turn and prints a summary line. A baud the UART cannot produce (divisor 0 or
  too large) counts as SKIP, not FAIL. ``auto_hs`` does the same for 230400,
  460800, 921600, 1152000 and 3686400. In both lists a baud whose real rate
  differs from the request by more than 3% (the divisor is an integer) is also
  SKIP, because both ends would agree on the wrong rate and still PASS. With a
  1.846 MHz UART clock (``clk / 16`` = 115384) every ``auto_hs`` rate is SKIP;
  these rates need a faster UART clock. The command returns an error if any
  rate FAILs or has a setup error.
* ``inc`` (default): byte value equals the offset, so an error offset maps to
  the expected value. ``fixed``: every byte is 0x55.
* ``len``: bytes per direction, default 256, maximum
  ``CONFIG_UART_BAUDRATE_TEST_MAX_LEN``.
* Both directions (A to B, then B to A) run on every call, at 8N1.

Output is one PASS or FAIL line per direction. On a mismatch the sample prints
the baud rate, the first error offset, the expected and the actual value, and
the total mismatch count. A timeout with zero bytes received usually means a
wiring problem.

Limits
******

* The command rejects a baud whose divisor (``clk / (16 * baud)``) is 0 or
  does not fit the 16-bit divisor latch, that is, a baud above ``clk / 16`` or
  below ``clk / (16 * 65535)``. The driver must include the divisor mask fix
  (``& 0xff`` on DLL); without it, divisors of 16 and above are truncated and
  both ends agree on a baud rate that was never produced.
* A PASS only means both ends agreed at that baud with 8N1 and the chosen
  length. There is no mismatched-baud negative test.
* The original UART configuration of both ports is restored after each run.

UDMA mode
*********

The overlay ``boards/ast1040_evb_ast1040_cm4.overlay`` has a define that
selects the mode. Edit its value and rebuild:

.. code-block:: c

   #define UART_UDMA_MODE 1   /* 1 = UDMA ring buffers, 0 = UART FIFO */

When it is 1, the overlay sets ``dma = <1>`` on every UART except uart4.
uart4 has no UDMA support and always runs with the FIFO, so a test that
involves uart4 mixes the two modes. In UDMA mode ``uart_poll_out`` writes into a 1 KB ring instead of
waiting for the FIFO, so transmission runs back to back at the line rate.

UART clock source
*****************

Each UART takes its input clock from UARTCLK (generated by SCU330) or HUARTCLK
(generated by SCU334). The choice is one bit per UART in SCU280. The sample does
not set it: it uses whatever the boot stage left, and the shell reports the rate
that the clock driver returns for that source.

To select the source, add the ``uart-clk-source`` property of the clock node to
``boards/ast1040_evb_ast1040_cm4.overlay``:

.. code-block:: devicetree

   &sysclk {
           uart-clk-source = <0x03>;   /* uart0 and uart1 on HUARTCLK */
   };

Bit x of the value is the source of UART x: 0 is UARTCLK and 1 is HUARTCLK.
When the property is present, every UART whose bit is 0 is set to UARTCLK,
including UARTs the value does not mention. Bits above 12 are ignored.

Keep in mind:

* HUARTCLK is only useful if an earlier boot stage has set the SCU334 N/R
  values and the HUXCLK divider in SCU284. The property does not program them.
* Both UARTs of a pair that are tested together must run from the same clock
  rate: the command refuses to run (setup error) if the clock or divisor of
  the two differ.

Building
********

.. code-block:: console
